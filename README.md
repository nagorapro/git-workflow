### GIT WORKFLOW ДЛЯ ИНЖЕНЕРОВ:

---
### Термины:

- *Trunk-based development* — разработка вокруг основной ветки.
- *Branch protection* — защита ветки.
- *CI (Continuous Integration)* — непрерывная интеграция.
- *Push* — отправка изменений.
- *Pull Request* — «запрос на слияние изменений».
- *PR template* — шаблон описания.
- *Atomic change* — атомарное изменение.
- *Code Review* — проверка кода.
- *Approve* — одобрения.
- *Freeze* — заморозка ветки.
- *Merge* — слияние веток.
- *Rebase* — перебазирование, перенос коммитов на актуальную базу.
- *History rewrite* — переписывание истории коммитов.
- *Squash merge* — слияние с объединением коммитов.
- *Force push* — принудительная отправка.
- *Force push with lease* — безопасная перезапись истории ветки.
- *Rebase and merge* — перебазирование и слияние.
- *Up-to-date* — синхронизировано.
- *Linear history* — линейная история.
- *Single owner* — один владелец (ветки).
- *Domain terms* — термины предметной области.
- *Abbreviations* — сокращения.
- *UI (User Interface)* — пользовательский интерфейс (frontend).
- *API (Application Programming Interface)* — программный интерфейс (backend).

---
### Архитектурные принципы:

- *Task-level detailed history* — детальная история в рабочей ветке задачи.
- *Action-level integration history* — агрегированная история по типам действий.
- *Atomic PR discipline* — атомарность: один файл = один рабочий коммит.
- *Deterministic commit grammar* — фиксированный формат подписей коммитов.
- *Controlled history rewrite* — контролируемое переписывание истории перед merge.
- *PR as integration boundary* — Pull Request как граница интеграции изменений.

---
### Стратегия ветвления:

- Основная ветка `main` защищена
- Разработка ведётся от ветки `main`
- Используются стандартизированные ветки задач
- Ветка создаётся от актуального состояния ветки `main`
- Каждая ветка соответствует одной задаче
- Прямые изменения в `main` запрещены
- Интеграция изменений только через PR
- Ветки не удаляются после слияния и не переиспользуются

---
### Категория задачи (task-category):

>`<task-category>` — отвечает на вопрос: «К какой категории относится данная задача?».

- **Типы:**
    - `feature` — новая функциональность
    - `refactor` — переработка без изменения логики
    - `improve` — улучшение с изменением логики
    - `bugfix` — исправление ошибки

---
### Объект задачи (task-object):

>`<task-object>` — это существительное, которое представляет объект, отвечает на вопрос: «Что именно создаётся или изменяется?».

- **Правила:**
    - Только `lowercase` (нижний регистр)
    - Только латиница
    - Длина — не более 3–5 слов
    - Слова разделяются через `-`
    - Без предлогов и лишних слов
    - Без глаголов в прошедшем времени
    - Без служебных слов (`the`, `a`, `fix`, `update` и т.д.)

- **Примеры:**
    - `<task-object>`
    - user-controller (services/user/controller.js)
    - user-service (services/user/service.js)
    - user-model (services/user/model.js)
    - accounting-transformer (toAccounting.js)
    - age-checker (checkAge.js)

---
### Ветка задачи (task-branch):

- **Формула названия ветки:**
    - `<category>/<domain>/<layer>/<object>`

- **Расшифровка:**
    - `category` — категория задачи (`feature`, `refactor` и т.д.)
    - `domain` — домен проекта (`admin`, `seller` и т.д.)
    - `layer` — слой, frontend или backend (`ui` или `api`)
    - `object` — объект (`service`, `module`, `config` и т.д.)

- **Примеры:**
    - `feature/admin/api/check-access` — добавление логики проверки доступа
    - `feature/seller/ui/product-service` — добавление нового продукта
    - `refactor/admin/api/agent-service` — переработка сервиса агентов
    - `improve/seller/ui/contract-creator` — улучшение flow создания контракта
    - `bugfix/integ/api/payment-handler` — исправление ошибки обработки платежей

### Правила оформления коммитов:

>Настоящий раздел определяет правила организации истории изменений и стандарты подписи коммитов в Pull Request.

- **Принципы организации коммитов:**
    - Один изменённый файл = один рабочий коммит для PR
    - Один рабочий коммит отражает одно логическое изменение одного файла
    - Каждый рабочий коммит для PR должен быть атомарным
    - Запрещено добавлять 2 и более файлов в один рабочий коммит для PR
    - Разрешено добавлять 2 и более файлов в один интеграционный коммит

- **Цель:**
    - Прозрачная и навигационная история изменений
    - Удобство Code Review
    - Контролируемая декомпозиция изменений
    - Корректное отображение Last commit в GitHub

- **Двухуровневая модель истории:**
    - История состоит из двух уровней
    - Рабочий уровень — ветка задачи, детальная история изменений
    - Интеграционный уровень — основная ветка, агрегированная история по действиям

- **Правила работы в Pull Request:**
    - В процессе разработки допускается несколько рабочих коммитов
    - Каждый рабочий коммит подписывается по установленному формату
    - Коммит фиксирует тип действия, а не название модуля
    - После одобрения (approve) выполняется редактирование истории (rebase)
    - Коммиты группируются по выполненным действиям над конкретными файлами
    - Интеграционный коммит отражает один тип действия и может включать N файлов
    - Интеграционный коммит может включать N файлов, но только одного `entityType`
    - Ветка задачи обязательно сохраняется для просмотра полной истории

- **Формат подписи рабочих коммитов:**
    - `<Глагол действие в прошедшем времени> <существительное>`
    - `<VerbPast> <entityType>`
    - `VerbPast` — глагол-действие в прошедшем времени
    - `entityType` — тип сущности (module, config, test и т.д.)

- **Допустимые глаголы (VerbPast):**
    - *Added* — добавлен
    - *Updated* — обновлён
    - *Refactored* — переработан
    - *Improved* — улучшен
    - *Fixed* — исправлен
    - *Renamed* — переименован
    - *Moved* — перемещён
    - *Deleted* — удалён
    - *Reviewed* — проверен

- **Типы сущностей (entityType):**
    - *module* — файл с логикой (.js)
    - *type* — файл с типами (.ts)
    - *config* — файл с конфигурацией (.js, .json, .yaml)
    - *mock* — файл с фейковыми данными (.js, .json, .yaml)
    - *schema* — файл со схемами для валидации (.js)
    - *template* — файл с шаблоном (.html, .xml, .sql)
    - *style* — файл со стилизацией (.css, .scss, .sass)
    - *test* — файл с тестами (.test.js)
    - *doc* — файл с документацией (.md, .txt)
    - *asset* — файл со статикой (.svg, .jpg, .png, .woff)

- **Примеры подписей рабочих коммитов:**
    - *Added module* (строго 1 добавленный модуль)
    - *Updated module* (строго 1 обновленный модуль)
    - *Refactored module* (строго 1 переработанный модуль)
    - *Improved module* (строго 1 улучшенный модуль)
    - *Fixed module* (строго 1 исправленный модуль)
    - *Renamed module* (строго 1 переименованный модуль)
    - *Moved module* (строго 1 перемещённый модуль)
    - *Deleted module* (строго 1 удалённый модуль)

- **Примеры подписей объединённых коммитов:**
    - *Added module* (от 1 до N добавленных модулей)
    - *Updated module* (от 1 до N обновленных модулей)
    - *Refactored module* (от 1 до N переработанных модулей)
    - *Improved module* (от 1 до N улучшенных модулей)
    - *Fixed module* (от 1 до N исправленных модулей)
    - *Renamed module* (от 1 до N переименованных модулей)
    - *Moved module* (от 1 до N перемещённых модулей)
    - *Deleted module* (от 1 до N удалённых модулей)

### Pipeline и flow для Pull Request:

- **Создание PR:**
    - PR создаётся из ветки задачи в ветку `main`
    - Одна задача = одна ветка = один PR
    - PR должен содержать структурированное описание по [PR template](https://github.com/nagorapro/git-workflow/blob/main/pr_template.md)
    - Файл [PR template](https://github.com/nagorapro/git-workflow/blob/main/pr_template.md) хранится в репозитории проекта
    - Путь к файлу [PR template](https://github.com/nagorapro/git-workflow/blob/main/pr_template.md): `.github/pull_request_template.md`
    - Описание PR содержит секции действий над файлами и полные пути к ним

- **Разработка в PR:**
    - Допускается несколько рабочих коммитов
    - Каждый коммит соответствует правилу `atomic change`
    - Каждый коммит подписывается: `<VerbPast> <entityType>`

- **Code Review:**
    - PR проходит обязательный Code Review
    - После `approve` ветка считается готовой к интеграции
    - После `approve` запрещено добавление новых коммитов
    - После `approve` возможны только «косметические» новые коммиты

- **History rewrite:**
    - После `approve` выполняется `rebase`
    - Коммиты группируются строго по `<VerbPast>` и `<entityType>`
    - Каждый интеграционный коммит отражает один `<VerbPast>` и один `entityType`
    - В одном интеграционном коммите не может быть `Added module` и `Added config`

- **Интеграционный коммит:**
    - В итоге может оказаться N интеграционных коммитов
    - В одном таком коммите не может быть `Added module` и `Added config`
    - В одном таком коммите всё либо только `Added module` либо `Added config` и т.д.

- **Force push:**
    - Используется только `--force-with-lease`
    - `--force-with-lease` — безопасная перезапись истории
    - `--force-with-lease` выполняется только после `history rewrite`
    - У ветки только один ответственный (`single owner`)

- **Merge:**
    - Для слияния используется только `Rebase and merge`
    - Ветка задачи должна быть актуальна относительно `main` (`up-to-date`)
    - Слияние выполняется только после финального состояния истории
    - В `main` попадают только агрегированные коммиты без `merge-коммита`
    - После слияния ветка задачи не удаляется, а сохраняется для истории
    - История в `main` ведётся по принципу `linear history`
